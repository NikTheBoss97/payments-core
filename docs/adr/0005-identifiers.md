# ADR-0005: Identifiers

- Status: accepted
- Date: 2026-10-14

## Context

Accounts, ledger transactions and entries need primary keys now; payments,
idempotency records and outbox events will need them later. Ledger rows are
never updated (ADR-0004), so a key that entries reference can never change.
The domain layer builds a complete, balanced transaction before writing it
(ADR-0004), and after a lost `COMMIT` the service must be able to find out
what happened.

## Options

| Option | Why not |
|---|---|
| **UUIDv7 generated in Rust** | Chosen |
| `BIGINT` identity assigned by PostgreSQL at insert | The ID exists only after the insert, and is easy to enumerate if exposed |
| `BIGINT` fetched before the insert (`nextval`, or hi-lo: reserving a block of values in one call) | Runner-up: a round trip before the ID exists (per insert, or per block with hi-lo), a sequence coupled to the domain layer and its tests, and payments would still need an opaque public ID |
| UUIDv4 | Random positions in the index: bigger indexes and more write-ahead log |
| UUIDv7 generated by PostgreSQL 18 as a column default (`DEFAULT uuidv7()`) | The ID exists only after the insert; fetching it first costs a round trip, as with `nextval` |
| ULID, KSUID | Non-standard versions of the same idea; a KSUID is 20 bytes |
| Snowflake-style 64-bit IDs | Worker IDs and clock hazards, built for sharding, which is a non-goal |
| UUIDv1, UUIDv6 | RFC 9562 tells new systems to use UUIDv7 |
| Internal `BIGINT` plus a public UUID | Two identifiers per row; premature |
| Name-based UUIDv5 or UUIDv8 | RFC 9562 advises against them as primary keys, and their index order is random |
| IDs chosen by the client (Google AIP-133) | Overlaps the idempotency keys of phase 3 |

## Decision

- `accounts`, `ledger_transactions` and, later, payments and outbox events
  use `uuid` primary keys holding UUIDv7 values generated in Rust
  (`Uuid::now_v7`, crate `uuid` 1.27 or later) through an injectable
  generator, so tests can use deterministic values.
- No database defaults, so an insert that forgets an ID fails instead of
  quietly getting one the service never saw. A CHECK requires version 7:
  `uuid_extract_version(id) IS NOT DISTINCT FROM 7`. A plain `= 7` would let
  the all-zero UUID through, because the function returns NULL for it and a
  CHECK that evaluates to NULL passes.
- `ledger_entries` uses the primary key `(transaction_id, line_no)`, with
  `line_no` running from 1 to the transaction's `entry_count` (ADR-0004). An
  entry has no identity outside its transaction, this key is exactly the
  lookup the commit-time check needs, and the table gets one index fewer.
- Business uniqueness uses explicit constraints, such as `(scope, key)` for
  idempotency records (phase 3) and `(psp, event_id)` for webhooks (phase 4).
- Rust newtypes (`AccountId`, `TransactionId`) stop one kind of ID from being
  passed where another is expected.

## Consequences

- IDs exist before any I/O: a whole transaction is built in memory, and its
  ID can appear in logs and outbox payloads before the write.
- Time-ordered keys insert at or near the right edge of the B-tree (the leaf
  page with the largest keys), so writes stay on a few pages, which are left
  about 90% full when they split. Random UUIDs insert all over the index,
  leave pages about 70% full and touch many more of them. PostgreSQL writes
  a page in full to the write-ahead log the first time it changes after each
  checkpoint, so random keys also produce far more log. The gap shows once
  the index no longer fits in memory; at demo scale it is small.
- A key takes 16 bytes instead of 8.
- IDs reveal their creation time to the millisecond. Within a millisecond,
  `Uuid::now_v7` uses a process-wide counter that starts at a random value
  and rises by one per ID, across all tables, so two IDs from the same
  millisecond show how many IDs the process created between them, and each
  further ID adds only 32 fresh random bits. They are not secrets, and
  authorization never relies on them.
- Nothing may page or cut off by ID (`WHERE id > $last_seen`), because a row
  with a smaller ID can still commit later: IDs are fixed before commit, and
  clocks can disagree. A later phase that needs a commit-order cut-off, such
  as the outbox relay (phase 5), must use something else, for example
  PostgreSQL's own transaction IDs (`xid8`, compared with
  `pg_snapshot_xmin`), never the ledger's `TransactionId`.
- After a lost `COMMIT`, looking the ID up is not enough: other sessions
  cannot see the first attempt's rows until it commits, and it may still be
  committing, so an empty result proves nothing. Recovery re-runs the
  identical insert with the same IDs on a new connection. PostgreSQL makes an
  insert that collides with a row from an unfinished transaction wait for
  that transaction to end. If the first attempt rolled back, the retry
  succeeds; if it committed, the retry fails with a duplicate-key error, and
  the service compares the stored entries with the intended ones: equal means
  already applied, different means a bug to report.
- If the `COMMIT` never reached the server, the first session can stay idle
  in its open transaction, holding its rows, until the server notices the
  dead connection, which with default TCP keepalive settings takes hours.
  The runtime role is therefore given an `idle_in_transaction_session_timeout`,
  and the retry runs with a `lock_timeout`; a timeout means the outcome is
  still unknown, and recovery tries again later.
- IDs generated by the service make only the hop from the service to
  PostgreSQL safe to retry: a client that retries after a timeout sends a new
  request, which gets new IDs. Client retries are handled by idempotency keys
  (phase 3, invariant I4).
- `uuid` 1.27, which fixed an ordering race in `now_v7` between threads,
  requires `rust-version` 1.89 or later.

## Amendments

- 2026-10-17: "No database defaults" covers identities, which the service
  must know before any I/O. A recording time is an observation, which the
  database stamps with `DEFAULT transaction_timestamp()` (ADR-0012).
- 2026-10-20: "through an injectable generator" means that the ledger's
  functions never create IDs: the caller creates each ID and passes it in
  as a value, using `TransactionId::now_v7()` or `AccountId::now_v7()`, the
  only calls to `Uuid::now_v7` in the library. Tests pass fixed IDs built
  by a helper under `tests/`. Opening an account takes a candidate ID,
  keeps the stored one when the business key already exists (ADR-0009),
  and runs outside any posting's database transaction, so a ledger
  transaction refers only to committed accounts and its retry stays
  identical. `TransactionId` is neither `Copy` nor `Clone`, so one ID
  cannot quietly serve two postings. Converting a `Uuid` into an ID checks
  version 7 and the RFC 9562 variant, exactly what the CHECK accepts:
  `uuid_extract_version` returns NULL for any other variant.
